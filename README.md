# 湖's Takeaway（云开发软件阶段）

当前版本已经接入真实微信云开发环境和 HM-10 + STM32 实体 BLE 链路。用户、协议同意、柜体、柜格业务状态、存取记录、反馈、客服授权、紧急请求、维修工单和审计日志以云数据库为业务事实来源；柜门 `OPEN/CLOSED` 来自 STM32 通过电子锁蓝白反馈返回的 `@STATUS`，不使用独立门磁。

除登录、用户协议、隐私政策和必要登录说明外，所有功能都要求先登录；柜体业务还必须同意当前版本协议。扫码启动时会保留 `pendingCabinetId`，登录和协议确认完成后才加载柜体并连接 BLE。

用户账号名由云端按照注册顺序自动分配为至少五位的编号，例如第一个用户为 `00001`、第二个为 `00002`。编号一经分配不可修改；既有账号会在更新后的首次登录时按照原注册时间补齐编号。

## 微信开发者工具运行

1. 打开微信开发者工具，选择“导入项目”。
2. 项目目录选择本文件夹；AppID 可使用测试号。
3. 不带扫码参数时不会绑定默认柜体，首页会提示扫描柜体二维码。
4. 测试扫码参数可在“编译模式”增加任意 `cabinetId`；小程序码 `scene` 支持 `cabinetId=某柜体ID` 或直接携带柜体ID。同时存在时以 `scene` 为准。
5. 首页进入“模拟柜体”，确认业务状态和门状态分别展示。
6. 首页进入“开发调试工具”，切换 BLE 状态、柜门 OPEN/CLOSED 或管理员业务状态。
7. 使用 ADMIN 或 DEVELOPER 模拟身份进入个人中心，可打开独立“管理中心”，查看多柜体电量和管理柜格维修状态。
8. 在“管理中心 → 柜体管理”中可动态新增、编辑或设置整柜维修，并复制 `scene=cabinetId` 所需参数。柜格数量在创建后不可修改；历史停用数据会统一迁移为维修中。
9. 使用客服、管理员或开发者身份进入“客服处理中心”，选择柜体和已有待取记录，核对顾客提供的取餐码与用户 ID 后签发一次性短时开锁授权。客服端不会连接柜体；顾客在自己的小程序中打开“客服开锁授权”，由顾客手机连接当前柜体 BLE 并执行。
   客服处理中心还可以直接输入用户 ID 或注册编号查看该用户操作记录；即使用户没有提交反馈或紧急请求，也可以先查轨迹再决定处理方式。
10. 紧急客服请求支持待核验、核验中、已授权、转现场维修、已解决、用户取消和过期状态；同一用户、同一业务记录不会重复创建多条处理中请求。
   用户未扫描柜体码时，可在客服页手动填写柜体编号和柜格编号；也可以先打开微信客服，在聊天中告知信息，再由客服在请求卡片中选择柜体和柜格补录。系统会校验实体柜格并自动关联当前未取餐记录。
11. 管理者可进入“维修工单”，完成接单、到场、现场四项检查、机械应急开锁记录、设备自检确认和恢复使用。硬件故障未自检或四项检查未全部正常时，恢复操作会被 Service 层拒绝。
12. 占用柜格实际已经为空时，管理员可使用“开柜核空”。系统先签发本柜格的短时授权并现场开柜，只有管理员再次确认柜内为空后，才把原待取记录标记为“管理员核空”并将柜格设为空闲；取消确认不会修改订单或柜格状态。

连接或新建 Mock 柜体不会自动生成任何存入记录。只有存餐人员输入用户手机号后4位、完成关门并点击“确认存入”后，系统才创建记录，并把该4位数字保存为取餐码。

调试门状态时只更新 `doorStatus`，不会联动 `status`。实体模式下门状态只能来自真实 `@STATUS`；`config/env.js` 中把 `IS_DEVELOPMENT` 改为 `false` 可隐藏首页调试入口。

## 多柜体测试

1. 在开发调试工具中输入任意第一个 `cabinetId`，修改一个柜格的门或业务状态。
2. 输入另一个 `cabinetId` 模拟扫码，确认首页当前柜体、BLE关联柜体和柜格数据均已切换。
3. 再切回第一个柜体，之前修改的状态应仍然保留，且不会污染第二个柜体。
4. 分别在两个柜体完成存餐；个人中心的累计数量应跨柜体汇总，记录卡片会显示各自的 `cabinetId`。

本地 Mock 数据按 `cabinetId` 分区。柜格操作、柜门状态事件、开锁命令、存入记录和反馈都显式携带 `cabinetId`；BLE连接状态属于当前手机会话，不写入共享柜体业务数据。

## 登录、隐私与云端迁移边界

微信云开发现已启用：`cloudService` 统一初始化及调用云函数；登录、隐私同意、柜体与柜格读取、存取主链路、客服处理、反馈、日志、柜体管理和维修工单均已接入云端。`USE_CLOUD=true` 时客户端隐藏 Mock 角色选择、禁用 `loginMock`，不信任本地缓存角色，并由云端再次检查登录、当前协议版本和操作权限。具体部署与索引要求见 `cloudfunctions/README.md` 和 `docs/CLOUD_DATABASE_INDEXES.md`。

当前已提供 Mock Auth、隐私协议版本确认、统一 Permission Guard、pendingCabinetId 恢复和 Mock OperationLog。开发配置默认自动登录/同意，以免阻塞演示；将 `MOCK_AUTO_LOGIN`、`MOCK_AUTO_CONSENT` 关闭后，可以测试扫码 → 登录 → 协议确认 → 恢复柜体 → BLE连接流程。

页面通过专用 Repository 访问用户、柜体、柜格、存入、反馈和操作日志数据。正式接微信云开发时替换 Repository/Service 实现，不在页面中改写业务流程。详细边界见 `docs/architecture.md` 与 `cloudfunctions/README.md`。

管理中心已与开发调试工具分离。设备在线状态来自当前手机已验证的 BLE 连接；`Cabinet.lastBleSeenAt` 记录最近一次实体柜体遥测同步。当前没有真实电池数据时不显示电量假值，未来电池字段接入后再展示。

管理中心新增“运营分析”，仅 `ADMIN/DEVELOPER` 可访问。页面按今天、近7天、近30天查看总览、使用情况、设备健康、故障维修和客服统计；统计在云函数中聚合，历史数据不足时显示“暂无数据”。新版本旁路记录 `operationEvents`，事件写入失败不会阻塞存餐、取餐或开柜。

开发调试页在 `BLE_TRANSPORT=MOCK` 时仍可模拟门锁故障。真实实体模式下，连续三次真实实体开锁失败后柜格才自动进入维修中；硬件自检通过前任何恢复请求都会被拒绝，管理中心可查看故障告警和完整操作记录。

开发调试页的“重置当前柜体 Mock 数据”会同步清理该柜体的存取、反馈、授权、客服请求、故障和维修工单，避免演示数据互相污染；不可修改的审计日志仍会保留。

柜体清单不写死在小程序代码中。新增柜体会通过 Repository 创建 Cabinet 与对应 Locker；正式状态只有正常和维修中，旧 `DISABLED/deletedAt` 数据仅作兼容迁移，不会删除历史记录。维修中柜体的二维码不会连接 BLE。

柜体详情按实体柜格逐格提供“设为维修、恢复使用”操作；占用柜格另提供受控的“开柜核空”，不能通过普通状态校正直接覆盖待取记录。

柜体管理列表提供“全部 / 正常 / 维修中”筛选，并汇总展示每台柜体的当前连接状态、最近通信时间、硬件故障格和维修格，便于多柜体扩张后的日常巡检。

整柜进入 `MAINTENANCE` 后，用户扫码、首页业务入口和柜格页面都会被拦截，提示整柜正在维修并提供客服入口；拦截发生在 BLE 连接之前。

开发调试页模拟“设备离线”时会触发整柜控制器故障：系统自动进入维修并断开 BLE。设备恢复在线只模拟控制器自检通过，管理员仍需在柜体详情中确认“恢复整柜使用”。

个人中心会按角色显示“反馈处理”：管理员、客服和开发者可以查看用户 ID、柜体、柜格及描述，并在后台标记处理中或已处理；这些内部状态不会增加用户端负担。

工作人员可从反馈直接进入用户操作轨迹，日志支持按用户、柜体、柜格、操作类型、成功/失败和日期范围组合查询。

开发登录页支持四种角色：`USER`、`ADMIN`、`CUSTOMER_SERVICE`、`DEVELOPER`。普通用户不再区分顾客和外卖员，同一个 `USER` 账号可以存餐和取餐；管理、客服、开发权限仍彼此分离，开发调试工具仅对开发者显示。

`ADMIN` 采用“客服 plus”权限模型：继承客服处理中心、反馈、取餐码核验、一次性授权签发和操作轨迹查询能力，并额外拥有柜体管理与维修能力；`CUSTOMER_SERVICE` 不具备管理权限，也不能通过互联网或自己的手机直接控制 STM32 柜体。

普通取餐与客服授权取餐都通过 `unlockExecutionService` 进入同一套“校验授权 → 手机 BLE → STM32 实体开锁 → 电子锁反馈 OPEN → 完成取餐”执行层。授权创建不等于开锁成功；一次性 token 在发起硬件尝试时即变为 `USED`。同一实体柜格连续三次真实电子开锁失败后，柜格进入 `REQUIRES_ONSITE_MAINTENANCE/MAINTENANCE`，停止继续电子授权。管理员记录现场机械应急开锁后，订单可完成，但柜格仍保持维修中，直至设备自检通过并由管理员确认恢复。

所有电子开锁（存餐、正常取餐、客服授权和维修测试）现在都必须携带统一硬件授权包。`lockService` 会拒绝无授权、字段被篡改、跨柜体/跨柜格及重复发送的命令；Mock 回归路径在模拟控制器接受命令时即消费授权，即使随后锁驱动失败也不能重放。实体 HM-10 + STM32 路径由云端授权、手机 BLE 和 STM32 协议共同校验；前端不暴露可任意创建授权的公共接口。

实体 BLE 链路使用 HM-10 的 FFE0/FFE1 特征和 STM32 文本协议：`@IDENTIFY`、`@OPEN:xx`、`@STATUS:xx`。协议说明见 `docs/BLE_ESP32_PROTOCOL.md`；Mock 传输仍保留用于开发回归，页面和开锁业务状态机不因传输层切换而重写。

未使用授权可以由用户主动放弃、由客服撤销，也会在柜体/柜格进入维修或停用、业务记录失效时自动撤销。撤销只代表授权不可再使用，不会伪造开锁或取餐成功。

个人中心的“取餐记录”只展示状态为 `PICKED_UP` 且已有 `pickedAt` 的成功记录，包括取餐时间、柜体、柜格和原取餐码。错误取餐码等失败尝试进入独立的 Mock 后台审计仓库，不会出现在用户取餐记录中。“我的存入记录”页面提供“全部 / 未取餐”筛选。

## 仍为开发/Mock 的部分

开发调试页中的 Mock 连接、模拟故障和本地回归能力仍然保留，但普通用户不能进入。正式实体模式已经使用 HM-10 文本 BLE 与 STM32 的 `@IDENTIFY`、`@OPEN`、`@STATUS` 链路。当前授权 token 仍使用云端短时占位格式，正式发布前仍需由云端签发不可伪造的签名授权，并由 STM32 独立验签、校验 cabinetId/lockerId/command/expiry/nonce，并持久化防重放状态；控制器不能回查或信任客户端 Repository。

## 自动检查

当前版本以微信开发者工具真机回归为主；本项目快照未包含旧版 `work/` 冒烟脚本。提交前至少执行全项目 JavaScript 语法检查，并按 `docs/roadmap.md` 完成实体 BLE、存取、遥测和维修恢复回归。

六步总路线见 `docs/roadmap.md`；第 1—3 步的原型链路已经完成，实体结构深化、发布级签名授权、电池遥测和第 4—6 步验收仍待完成。
